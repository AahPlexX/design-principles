Forms & Inputs

A form is any part of a page where someone types, selects, or uploads something. Form design is about removing every point of friction and confusion between "I want to submit this" and actually submitting it.

Why it matters

Forms are where a site asks something of the reader instead of just giving them information, and that's exactly where people quit. A confusing error message, a field whose purpose isn't clear, or a validation rule discovered only after submitting is often the single biggest drop-off point in a signup, checkout, or contact flow.

The core rule

Every field needs a visible label, a clear reason for existing, and an error message that says exactly what to fix — shown as close to the moment of the mistake as possible, not only after a full-page submit. If you can't explain why a field is required, remove it.

Good vs. bad

Good 
<label for="email">Email</label>
<input id="email" type="email" required>
<p id="email-err" role="alert">
  Enter an email with an @ symbol,
  like name@example.com
</p>

A real label, the right input type (brings up an email keyboard on mobile), and an error that tells you exactly what a valid answer looks like.

Bad 
<input type="text" placeholder="Email">
<p>Invalid input</p>

The label disappears once you start typing, the input type doesn't help mobile keyboards, and "Invalid input" gives no clue what was wrong or how to fix it.

Common mistakes

  • Placeholder text used as the only label. It vanishes the moment someone starts typing, so if they get interrupted or scroll back up, the field's purpose is gone. Use a persistent, visible label.
  • Vague error messages. "Invalid input" or "Something went wrong" forces the reader to guess. Say what's wrong ("Password needs at least 8 characters") and, ideally, how to fix it.
  • Validating only on submit. Waiting until the whole form is submitted to reveal an error made three fields ago means the reader has to scroll back and re-find their mistake. Validate a field once the reader has finished with it, not only at the very end.
  • Asking for information the task doesn't need. Every extra field is another chance to abandon the form. If a field's answer isn't used anywhere, remove it.
  • Wrong input type or keyboard. A phone number field using type="text" brings up a full alphabetic keyboard on mobile instead of a numeric one — a small thing that adds friction to every single user on a phone.

Checklist

  • Every field has a persistent, visible <label> — not just a placeholder.
  • Error messages state the specific problem and, where possible, the fix.
  • Fields validate as the reader finishes each one, not only on final submit.
  • Input types match the data (email, tel, number) so mobile keyboards adapt.
  • Every field's purpose could be explained in one sentence — if it can't, it's cut.
  • Required fields are marked clearly, not implied.
Go deeper

Autocomplete attributes: autocomplete="email", autocomplete="name", autocomplete="street-address", and similar values let the browser fill known fields automatically, which measurably speeds up form completion and reduces typos.

Associating errors with fields for screen readers: pairing aria-describedby on the input with the error message's id means a screen reader announces the error when the field receives focus, not only when it's visually near the input.

Multi-step forms: breaking a long form into steps can reduce the perceived effort, but only if progress is visible (a step indicator) and answers are preserved when someone goes back — an invisible multi-step flow just adds extra clicks without the psychological benefit.
