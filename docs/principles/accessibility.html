Accessibility

Accessibility is designing a site so it still works for someone who can't use a mouse, can't see the screen, or can't see it well — using only a keyboard, a screen reader (software that reads the page aloud), or magnification.

Why it matters

This isn't a small edge case: it covers permanent disabilities, temporary ones (a broken arm, eye surgery recovery), and situational ones (holding a baby in one arm, bright sunlight washing out a screen). A site built only for a mouse and perfect eyesight excludes all of these, often by accident — a missing label, a color-only signal, a click handler that only fires on a mouse event.

The core rule

Everything a mouse can do, a keyboard must also be able to do — and everything shown visually needs a text equivalent a screen reader can announce. If you can't tab to a control and activate it with Enter or Space, and you can't tell what it is with your eyes closed, it's not accessible yet.

Good vs. bad

Good 
<button aria-label="Close dialog">
  <svg aria-hidden="true">...</svg>
</button>

A real <button> is keyboard-focusable and clickable by default, and the label tells a screen reader what it does even though the visible content is just an icon.

Bad 
<div onclick="closeDialog()">
  <svg>...</svg>
</div>

A <div> isn't focusable or keyboard-activatable by default, and with no label, a screen reader announces nothing useful — this control is invisible to anyone not using a mouse.

Common mistakes

  • Building custom controls out of <div> or <span>. Native elements (<button>, <a>, <input>) come with keyboard behavior and screen-reader semantics built in. Recreating a button from a div means re-implementing all of that by hand, and it's usually incomplete.
  • Images with no alt text, or bad alt text. A missing alt attribute makes a screen reader announce the filename; decorative images should have alt="" so they're skipped entirely, not described.
  • Form fields with no visible, connected label. Placeholder text is not a label — it disappears the moment someone starts typing, and some screen readers don't announce it at all. Use a real <label> tied to the input.
  • Focus styles removed for looking "messy." outline: none with nothing to replace it removes the only visual signal a keyboard user has for where they are on the page.
  • Content that only appears on hover. A tooltip or menu that only shows on mouse hover is unreachable by keyboard and untouchable on a phone — it needs a focus and/or tap equivalent.

Checklist

  • Every interactive element is reachable and operable with Tab, Enter, and Space alone.
  • Focus is always visible — never removed without a replacement style.
  • Every image has appropriate alt text (or alt="" if purely decorative).
  • Every form field has a real, connected <label>.
  • Nothing important is conveyed by hover alone.
  • Headings are structured in order (one <h1>, then <h2>, etc.) so a screen reader user can navigate by heading.
Go deeper

WCAG's four principles (POUR): content should be Perceivable (available to the senses, e.g. via alt text or captions), Operable (usable via keyboard and other input methods), Understandable (clear language and predictable behavior), and Robust (works with current and future assistive technology, largely via correct HTML semantics).

ARIA is a patch, not a first choice. ARIA attributes (role, aria-*) exist to describe custom components that HTML has no native element for. The first rule of ARIA is: if a native HTML element already does what you need, use that instead of adding ARIA to a div.

Testing without a mouse: unplug your mouse (or just don't touch it) and try to complete your site's core task using only Tab, Shift+Tab, Enter, and Space. This alone catches a large share of accessibility issues before any specialized tooling is involved.
