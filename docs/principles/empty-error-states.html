Empty & Error States

An empty state is what a reader sees when there's genuinely nothing to show yet — an inbox with no messages, a search with no matches. An error state is what they see when something has gone wrong. Both are real screens that need real design, not a blank gap left over after the "actual" design was finished.

Why it matters

Empty and error states are often the very first thing a new user experiences — a brand-new account with zero data in it, or a search typo that turns up nothing. A blank white screen or a raw stack trace at that exact moment reads as broken, even when the underlying system is working exactly as intended. First impressions formed by an unhandled edge case are just as real as ones formed by the polished happy path.

The core rule

Every empty or error state needs three things: what happened, in plain language; why, if that's useful and knowable; and what to do next. A state missing all three isn't a screen, it's a dead end.

Good vs. bad

Good 
<div class="empty-state">
  <h2>No projects yet</h2>
  <p>Create your first project
     to get started.</p>
  <button>New project</button>
</div>

Names the situation, and gives the reader something to do about it immediately, without needing to hunt for the right button elsewhere on the page.

Bad 
<div class="empty-state">
  <p>No data</p>
</div>

States the fact and stops there — a brand-new user has no idea whether this is expected, broken, or something they need to fix.

Common mistakes

  • Rendering nothing at all for an empty state. A section that collapses to a blank gap with no heading or explanation reads as a loading glitch, not an intentional "there's nothing here yet."
  • Generic error text with no next step. "Something went wrong" tells the reader there's a problem without telling them whether to wait, retry, or give up — always pair an error with an action.
  • Showing raw technical detail to end users. A stack trace or a bare HTTP status code is meaningful to a developer and alarming or meaningless to almost everyone else — translate it into plain language before it reaches the reader.
  • Treating every empty state the same. "You haven't created anything yet" and "no results match your filters" are different situations that need different messages — the first needs encouragement to start, the second needs a way to loosen the search.
  • Error states with no way forward. A failed page load with no retry button, no link back, and no contact option leaves the reader stuck exactly where the error occurred.

Checklist

  • Every empty state explains why it's empty and suggests a next action.
  • Error messages use plain language — no raw codes or stack traces shown to users.
  • "Nothing here yet" and "nothing matches your filter" are worded differently.
  • Every error state offers a way forward: retry, go back, or get help.
  • Empty and error states were actually designed, not left as an unstyled placeholder.
Go deeper

Loading vs. empty. A skeleton screen (a gray placeholder shaped like the content that's coming) communicates "this is still loading"; an empty state communicates "this finished loading, and there's genuinely nothing here." Using the same visual for both makes a reader wait for content that was never coming.

404 pages as a design surface. A broken link is already a moment of friction — a 404 page that offers search, a link home, and possibly the page's likely intended destination turns a dead end back into forward progress.

Offline states. For anything that works (or partly works) offline, a distinct "you're offline" state — separate from a generic error — sets the right expectation and can point to what's still available without a connection.
