Responsive Design

Responsive design means one layout adapts to fit whatever screen it's shown on — a phone, a tablet, a laptop, a 32-inch monitor — rather than a separate design being built for each.

Why it matters

There is no single screen size to design for anymore, and there hasn't been for a long time. Over half of most sites' traffic is mobile. A layout that only works at one width either breaks (overlapping text, buttons cut off) or forces the reader to pinch-zoom and scroll sideways — both of which are enough friction that people leave.

The core rule

Design the layout to respond to the content running out of room, not to a fixed list of device widths. Use flexible units (percentages, fr, ch, rem) and let CSS Grid or Flexbox reflow content, adding a breakpoint only at the point where the current layout actually starts to look bad — not at "iPhone size" or "iPad size" as guesses.

Good vs. bad

Good 
.cards {
  display: grid;
  grid-template-columns:
    repeat(auto-fit, minmax(15rem, 1fr));
  gap: 1rem;
}

The grid fits as many 15rem-minimum columns as the available width allows — 3 columns on a wide screen, 1 on a phone — with no breakpoint needed at all.

Bad 
.cards { width: 1200px; }
.card { width: 380px; float: left; }

Fixed pixel widths mean the layout is correct at exactly one browser width and broken (overflowing, cut off, or forcing horizontal scroll) everywhere else.

Common mistakes

  • Designing only for one width, then "making it responsive" afterward. Retrofitting flexibility onto a fixed-width design usually means patching over symptoms; starting fluid avoids most of the problem.
  • Breakpoints chosen by device name instead of by content. "iPhone, iPad, desktop" isn't a real category system — screen widths are continuous, and new device sizes appear constantly. Add a breakpoint where your specific layout breaks, not at a guessed device width.
  • Text that doesn't reflow, only shrinks. Squeezing a fixed-width column onto a phone by shrinking font size instead of letting the column narrow and text wrap makes everything hard to read instead of just re-laid-out.
  • Touch targets sized for a mouse pointer. A link or button under about 44×44px is hard to tap accurately with a finger, even if it's perfectly clickable with a precise mouse cursor.
  • Hiding content on mobile instead of re-prioritizing it. "Just hide it on small screens" often removes something a mobile user specifically needed (like a phone number or address), rather than re-arranging it to fit.

Checklist

  • No horizontal scrolling at any viewport width from ~320px up.
  • Layout uses flexible units and wrapping (Grid/Flexbox), not fixed pixel widths for containers.
  • Breakpoints are placed where the specific layout breaks, not at guessed device sizes.
  • Tap targets are at least 44×44px on touch devices.
  • The page has a <meta name="viewport" content="width=device-width, initial-scale=1"> tag.
Go deeper

Container queries: media queries respond to the browser viewport's size; container queries (@container) let a component respond to the size of its own containing element instead, which matters once the same component (a card, a sidebar) can appear in differently-sized contexts on the same page.

Mobile-first CSS: writing base styles for the smallest screen and adding complexity with min-width media queries as space increases tends to produce simpler, more resilient CSS than starting from a desktop layout and subtracting for mobile with max-width queries.

clamp() for fluid values: clamp(min, preferred, max) lets sizes (font size, padding, width) scale smoothly with viewport width between a floor and a ceiling, often removing the need for a breakpoint entirely for that property.
