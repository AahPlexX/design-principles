Level 6, Lesson 5: Responsive spacing scale — shrinking vs. clamp()

A spacing scale built for a wide desktop screen often feels oversized on a phone. There are two common fixes: swap in a smaller scale at a breakpoint, or let one value flow smoothly between a floor and a ceiling instead of jumping at all.

A card's padding is set with two rules:

.card { padding: 32px; }

@media (max-width: 600px) {
  .card { padding: 16px; }
}

Resizing the browser slowly from 700px down to 500px wide, what does the padding do — and how would replacing both rules with padding: clamp(16px, 4vw, 32px); change that?

A media query is a threshold: the padding is 32px for every width down to 601px, then instantly 16px at 600px and below — a visible snap at one exact pixel. clamp(minimum, preferred, maximum) — here clamp(16px, 4vw, 32px) — instead evaluates a fluid preferred value (4vw, 4% of the viewport width) at every size, only locking to the 16px floor or the 32px ceiling once that fluid value would otherwise fall outside that range. The result is padding that shrinks continuously as the window narrows instead of holding still and then snapping. Neither approach is wrong: a breakpoint-based scale is simpler to keep in sync with the rest of a design system's fixed spacing tokens, while clamp() is the better choice when the resize itself needs to look smooth rather than stepped.
