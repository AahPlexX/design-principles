Level 2, Lesson 3: Spacing as design tokens — naming vs. raw values

A product goes through a visual refresh, and the spacing scale needs to shift slightly denser across the board. One codebase has "margin: 16px" typed into 200 different component files. Another has "margin: var(--space-md)" in those same 200 places, with "--space-md: 16px" declared once. Only one of those codebases gets to change its mind in a single edit.

A design system defines --space-md: 16px; once, and every component references var(--space-md) instead of typing 16px directly. What's the actual benefit of that named token over the raw value?

A design token is just a named stand-in for a value — here, a CSS custom property like --space-md that holds 16px and gets referenced by name instead of the raw number being retyped everywhere. The scale from the earlier lessons (pick every value from a fixed set of multiples) still decides what the number is; tokens are the naming layer on top that makes that scale maintainable. The real payoff shows up when the value needs to change: edit the one declaration, and every component that referenced --space-md updates with it. A raw 16px typed in 200 places has no such single point of change — someone has to find and edit all 200. Tokens don't shrink file size in any meaningful way, don't make spacing appear without one being applied, and don't add any responsive behavior on their own — that would require a media query or a fluid unit, not a naming convention.
