# Vite + React + Tailwind rewrite of the hand-written HTML site

This replaces 173 hand-written HTML files under `docs/` with a Vite + React + TypeScript + Tailwind v4
application, prerendered at build time back to 173 static HTML files served from the same GitHub Pages
subpath. Content (principle prose, quiz questions/options/feedback, course descriptions) is migrated
verbatim through a one-off extraction script and then hand-reviewed; the presentation layer — templates,
navigation, search, progress tracking, print handling, theme switching — is rebuilt from scratch on top of
typed content modules that are now the single source of truth. Thirteen custom "gate" scripts (URL parity,
content invariants, W3C validity, internal links, axe accessibility, contrast, performance budget, SEO)
run in CI and locally via `npm run gate:all`, and 45 unit tests exercise the client-side quiz/progress and
search enhancers against real rendered markup rather than hand-written fixtures.

I ran the full toolchain against this branch: `npm run typecheck`, `npm run test` (45/45 pass), `npm run
build` (173 pages prerendered, matching the legacy page count exactly), and all 13 `gate:all` checks
(format, lint, types, content invariants, contrast, tests, build, URL parity, internal links, SEO,
accessibility, performance budget, W3C HTML validity) — all pass clean, including the URL-parity gate
against the checked-in snapshot of the pre-migration site's exact 173 URLs.

**Watch for:** one confirmed accessibility regression in the desktop nav — `aria-current="true"` is set on
the Principles/Craft section links instead of `aria-current="page"`, which the pre-migration site used
(**confirmed**; not caught by `gate:a11y` because its sampled pages never render the header in the
`section: "principles"` / `section: "craft"` state). Everything else found is a nit.

**Verdict**: APPROVED

## High-level view

URL parity is airtight, which is what matters most on a GitHub Pages site with no redirect mechanism: the
route table in `src/lib/routes.ts` is the single source both the prerenderer and `gate:urls` read from,
and it emits exactly the 173 paths the legacy `docs/` tree served, byte for byte, `.html` suffix included.
localStorage compatibility gets the same treatment — the `theme` and `craft-progress` keys, their value
shapes, and both lesson-id formats (`lesson-3` vs `level-2-lesson-3`) are preserved and covered by tests
that assert the raw stored JSON, including a regression test for a real bug (an array value silently
discarding progress) caught and fixed mid-migration.

Content fidelity is very high. Every principle, course, and lesson I spot-checked — including a
math-heavy color-contrast lesson and a full principle page — matches the legacy HTML's prose, code
samples, and quiz text exactly, modulo a small number of deliberately disclosed copy changes (the craft
index blurb, the home `<title>`, the 404 body's phrasing to match the redesigned header) that are called
out in commit messages and don't touch the six-section principle skeleton the tone rules govern.

The enhancer/DOM contract — quiz answering, progress badges/meters, search filtering, theme toggling,
print expansion — is a faithful and in places improved port of the legacy vanilla-JS scripts, verified by
45 unit tests that render the real page components and attach the real enhancer rather than testing
against hand-written fixtures. The theme and print enhancers have no equivalent test file (no
`theme.test.ts` or `print.test.ts`), unlike `progress.ts` and `search.ts`.

The CI/Pages rewrite carries two explicitly recorded workarounds — a missing `environment:` protection
block on the deploy job, pending a repo-admin fix, and injecting `speculationrules` from JS rather than a
script tag because the W3C validator this repo gates on doesn't yet recognize that script type — each
documented in-file with the exact error that necessitated it.

### The `aria-current` value on desktop nav links

`SiteHeader.tsx`'s CSS class list keys visual "current" styling off the attribute's mere presence:

```
const linkClass =
  "... aria-[current]:text-ink aria-[current]:bg-surface";
```

so the *visual* state is correct regardless of the value. The value itself is wrong for two of the four
links:

```tsx
aria-current={section === "home" ? "page" : undefined}        // Home — correct
aria-current={section === "principles" ? "true" : undefined}  // Principles — should be "page"
aria-current={section === "craft" ? "true" : undefined}       // Craft — should be "page"
aria-current={section === "about" ? "page" : undefined}       // About — correct
```

`aria-current` accepts `page | step | location | date | time | true | false`. `"true"` is a legal value,
but it announces something different to a screen reader than `"page"` — it's the generic "current item in
a set" signal, not "this represents the currently displayed page," which is specifically what a
primary-nav link pointing at the page you're on should say. The legacy site used `aria-current="page"`
uniformly on the equivalent nav link (`docs/index.html`, `aria-current="page"` on Craft), and the same
codebase's `Breadcrumb.tsx` and mobile-menu principle link both use `"page"`. Two of the four links in the
one component that renders this pattern disagree with the other two and with the rest of the codebase —
**confirmed** by reading the component; nothing in the diff or commit messages explains the split, so this
reads as a copy-paste inconsistency rather than a deliberate choice.

This didn't surface in `gate:a11y` because its page sample (home, about, 404, two principle pages, craft
index, two course overviews, four lesson pages) never exercises `SiteHeader` in the `section: "principles"`
or `section: "craft"` state on a sampled page. It also wouldn't necessarily surface as an axe-core
*violation* even on a page that did — axe treats an unexpected `aria-current` value as "needs review," not
a hard failure. Fix: change both instances to `"page"`.

</details>
